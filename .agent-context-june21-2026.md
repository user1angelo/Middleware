# Project Context: Middleware (SOAR Framework)

This repository implements a Security Orchestration, Automation, and Response (SOAR) middleware bridging detection (Wazuh), analysis (ThreatContextStore), and response (WorkflowEngine + SDN/OpenDaylight).

---

## 1. Tech Stack & Architecture Pattern

An event-driven microservices architecture communicating via **RabbitMQ** message queues and storing data in **PostgreSQL**.

*   **SDK & Integrations:** Java 17/21 (Maven POM structure).
    *   Submodules: `nis-thesis-sdk`, `user-defined-modules` (Suricata, Zeek, OpenDaylight SDN, PRTG), and `ModuleRegistryLifecycleManager`.
*   **Web Dashboard:**
    *   **Backend:** NodeJS / Express.
    *   **Frontend:** React (Plain JS/CSS, no CSS frameworks like Tailwind unless requested).
*   **Message Broker:** RabbitMQ.
    *   `alerts_queue`: Raw alerts from detectors (Wazuh, etc.) to ThreatContextStore & WorkflowEngine.
    *   `workflow_response_queue`: Actions generated by WorkflowEngine or webapp directed to SDK modules.

## 2. Directory Anatomy

```
.
├── nis-thesis-sdk/               # Shared SDK library containing CoreSystemApi, ModuleHelper, & event schemas
├── user-defined-modules/         # Maven module implementing integrations (e.g., OpenDaylightModule, SuricataModule)
├── ThreatContextStore/           # Consumes alerts from RabbitMQ, stores to PostgreSQL (Uses direct javac builds)
├── WorkflowEngine/               # Evaluates incoming alerts against YAML playbooks, generates mitigation commands
├── webapp/                       # Node/React control dashboard
│   ├── backend/                  # Express REST API, processes, & ODL/Workflow adapters
│   └── frontend/                 # React UI for configs, logs, workflow viewer, and network control
├── ModuleRegistryLifecycleManager/ # Controls lifecycle/loading of user-defined modules
└── ThreatContextStoreTester/     # Verification/simulation tool for generating synthetic alerts
```

## 4. Guardrails & Quirks

*   **Build Scripts:** Build mechanisms vary:
    *   Use `mvn clean install` for `nis-thesis-sdk` and `user-defined-modules`.
    *   Use direct `javac` commands referencing local dependencies under `lib/*` for `ThreatContextStore` and `WorkflowEngine`. Do not attempt `mvn` commands on these directories.
*   **Classpath Separators:** Use `;` for Windows environments and `:` for Linux/macOS when building/running Java commands.
*   **Web Development CSS:** Do not install styling/framework dependencies like TailwindCSS unless explicitly instructed by the user. Use vanilla CSS rules inside `index.css` and local stylesheets.

## 5. Telemetry & Latency Benchmarking (Thesis Additions)

An end-to-end telemetry system propagates time performance metrics starting from the intrusion detection log up to SDN flow installation:
*   **Source (`SuricataModule.java`):** Parses event timestamp and adds `telemetry` JSON with `alert_generated_time_ms`, `system_received_time_ms`, and `alert_to_received_delay_sec`.
*   **Orchestration (`WorkflowExecutor.java`):** Captures `workflow_execution_time_ms` and computes `received_to_workflow_delay_sec`.
*   **Routing (`SdkModuleHost.java`):** Carries the JSON-based telemetry configuration objects down into the pluggable SDK modules.
*   **Enforcement (`OpenDaylightModule.java`):** Calculates ODL flow application delay and writes a comprehensive formatted benchmark diagnostic report directly to logs/web interface logs view.
