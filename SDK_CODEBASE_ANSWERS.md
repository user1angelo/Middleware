## Chapter 5 — System Implementation

### 5.2.2 SDK programming model and deployment

1. **Both models exist; they must not be described as one uniform deployment.** `nis-thesis-sdk` is a JAR library (`nis-thesis-sdk/pom.xml:12-13`) used by the `user-defined-modules` Maven module (`user-defined-modules/pom.xml:24-30`). SDK modules are embedded in the registry JVM: `SdkModuleHost` reflects and instantiates `OpenDaylightModule`, `SuricataHttpModule`, and `ZeekHttpModule` (`ModuleRegistryLifecycleManager/src/main/java/com/yourorg/registry/SdkModuleHost.java:289-311`). In contrast, `SuricataModule` is explicitly a standalone Java process using RabbitMQ (`user-defined-modules/src/main/java/com/nis1/thesis/udm/SuricataModule.java:25-39,82-159`).
2. **RabbitMQ is external and configurable, not embedded in the SDK.** The active configurations specify `rabbitmq.host=localhost` and port `5672` (`ModuleRegistryLifecycleManager/config.properties:8-19`; `WorkflowEngine/config.properties:7-18`; `ThreatContextStore/config.properties:8-14`). The code creates a client connection from these values (`WorkflowQueueListener.java:33-40`; `AlertBroadcastListener.java:43-50`). There is no broker Docker/container/VM definition in the repo, so its physical host cannot be confirmed; it can be changed through properties.
3. **There are central runtime processes.** `ModuleRegistryMain.main()` starts the registry, listeners, health monitor, and embedded SDK host (`ModuleRegistryMain.java:33-63`); `WorkflowEngineMain.main()` starts the workflow listener (`WorkflowEngineMain.java:17-57`); and `ThreatContextStoreMain.main()` starts storage/listener services (`ThreatContextStoreMain.java:21-55`). The SDK itself has no `main()`; `CoreSystemApi` is only an interface (`CoreSystemApi.java:21-61`).
4. **`initialize(CoreSystemApi)` is called by the host via reflection and constructor injection.** `initializeSingleModule` creates a no-argument module instance and calls `module.initialize(api)` (`SdkModuleHost.java:296-312`). `OpenDaylightModule.initialize` stores the API and creates `ModuleHelper` (`OpenDaylightModule.java:62-84`). This is neither a DI framework nor a static factory.
5. **The supplied launcher deploys separate JVM processes for the Threat Context Store, Workflow Engine, and Module Registry, plus Node backend/frontend processes.** See the five launches in `start-all.sh:66-93`. The OpenDaylight SDK module runs inside the Module Registry process; standalone UDMs may be launched separately. No Dockerfile or compose file was found, so a container-per-module or one-VM-per-module deployment is not evidenced.
6. **The SDK has Maven coordinates but no publication/repository configuration.** It is `com.nis1.thesis:nis-thesis-sdk:1.0-SNAPSHOT` (`pom.xml:7-10`, `nis-thesis-sdk/pom.xml:6-13`), and dependent modules reference that coordinate (`user-defined-modules/pom.xml:25-30`). The root reactor builds it as a monorepo module (`pom.xml:21-25`). README instructs `mvn clean install` (`README.md:65-84`), which installs locally; no `<distributionManagement>` or remote repository is declared.

### 5.2.2 How a module uses the SDK

7. **Minimum embedded-SDK implementation:** implement `PluggableModule`, provide `getName()`, `initialize(CoreSystemApi)`, and `shutdown()` (`PluggableModule.java:20-61`). In `initialize`, retain `api`, optionally construct `ModuleHelper`, and subscribe with `api.subscribeToEvent(...)`; `OpenDaylightModule` is the concrete pattern (`OpenDaylightModule.java:32,62-93`). It must also be made known to the host: currently the class name is manually listed in `SdkModuleHost.initializeModules()` (`SdkModuleHost.java:289-294`), so merely writing the class is insufficient for embedded loading.
8. **For embedded modules, the host calls `shutdown()` during registry shutdown and catches failures** (`ModuleRegistryMain.java:129-133`; `SdkModuleHost.java:365-375`). There is no SDK-level generic resource cleanup; each module owns its resources. For standalone Suricata, cleanup is a JVM shutdown hook plus `finally` executor shutdown (`SuricataModule.java:131-158`), not the `PluggableModule` contract.
9. **Registration is hybrid, not a single manifest.** Standalone UDMs publish a `registration` message to RabbitMQ (`SuricataModule.java:165-198`); `AlertBroadcastListener` calls `registry.registerModule` (`AlertBroadcastListener.java:118-121,151-157`), which stores in memory and PostgreSQL (`ModuleRegistry.java:123-164`). At registry startup, JARs in `modules.root` are scanned and placeholder records are made (`ModuleRegistry.java:313-326,386-474`). Embedded SDK classes are still an explicit hard-coded list, then auto-registered (`SdkModuleHost.java:289-317,330-355`).
10. **The SDK API exposes only publish/subscribe, but full decoupling is not enforced across the codebase.** `CoreSystemApi` contains only those two methods (`CoreSystemApi.java:21-61`), yet embedded modules share an in-process `SdkModuleHost` dispatcher (`SdkModuleHost.java:107-136`), and `OpenDaylightModule` writes `/tmp/middleware_scan_results.json` (`OpenDaylightModule.java:257-274`). Direct Java references and RabbitMQ queues remain possible outside the API.
11. **No generic publish retry is implemented.** `RealCoreSystemApi.publishEvent` catches and logs broker errors (`SdkModuleHost.java:62-93`) and returns; it does not retry or rethrow. The standalone Suricata publisher lets `IOException` propagate from `publishSuricataAlert` (`SuricataModule.java:405,481-482`) but per-line parsing catches/logs it (`SuricataModule.java:333-337,397-399`).

### 5.2.8 SDK ingestion process

12. **Raw Suricata path:** `SuricataModule.startEveJsonMonitoring` watches the configured `suricata.eve_json_path` using Java `WatchService` and tails only appended lines (`SuricataModule.java:294-364`; config load at `691-720`). It calls `parseEveJsonLine`, which filters for `event_type == "alert"`, then calls `publishSuricataAlert` (`SuricataModule.java:370-400`). No Filebeat/log shipper is used by this module. The alert is published to the default exchange with routing key/queue `workflow_queue` (`SuricataModule.java:479-482`).
13. **The standalone Suricata flow does not create `Event<T>` or SDK `NidsAlertData`.** Gson deserializes EVE JSON into private `SuricataEveLog` (`SuricataModule.java:377`; mapped fields at `740-785`), then builds `SuricataAlertData` and places Gson JSON under `payload` (`SuricataModule.java:443-477`). `NidsAlertData` is an SDK model used by `ModuleHelper.publishNidsAlert` (`ModuleHelper.java:79-83`), not by `SuricataModule`.
14. **The implemented fabric uses named durable queues via RabbitMQ’s default exchange, not a topic exchange or topic routing keys.** The workflow listener declares `workflow_queue` and `workflow_response_queue` (`WorkflowQueueListener.java:42-47`) and consumes `workflow_queue` (`187-190`). Publishers use `basicPublish("", queueName, ...)`, e.g. Suricata (`SuricataModule.java:481-482`), broadcast (`AlertBroadcastListener.java:209-213`), and workflow command (`WorkflowExecutor.java:160-165`). No `exchangeDeclare` or `queueBind` exists in the production Java paths. The topic-exchange wording in `CoreSystemApi` Javadoc (`CoreSystemApi.java:24-29`) is not implemented by this runtime.
15. **Workflow selection is content-based, with an exact message `event_type` gate; it is not RabbitMQ-routing-key based.** `WorkflowMatcher` checks workflow trigger event type against `alert.event_type` (`WorkflowMatcher.java:39-45`) and then evaluates selected payload fields from the YAML condition: alert type/category/note type, severity, signature, SID, and threat score (`89-236`). The listener reloads all YAML files for every alert (`WorkflowQueueListener.java:97-100`).
16. **Action target selection is dynamic at the registry layer, but the command type comes from workflow YAML.** `WorkflowExecutor.executeStep` sets `commandType` from the YAML event type (`WorkflowExecutor.java:104-128`) and publishes it. `CommandRoutingListener` selects a named `target_module` when supplied, otherwise `registry.findModuleByCapability(command)` (`CommandRoutingListener.java:123-143`); embedded modules are dispatched in memory while ordinary UDMs receive a queue message (`151-173`).
17. **There is broker queueing with consumer prefetch, not application-level backpressure.** The workflow listener uses manual ACK and `basicQos(10)` (`WorkflowQueueListener.java:42-47,161,187-190`), so RabbitMQ retains unacknowledged/queued messages. There is no explicit rate limiter, bounded executor, overflow policy, or producer flow-control code.
18. **Malformed workflow messages are retried once and then discarded; there is no DLQ declaration.** JSON parsing happens in the `DeliverCallback` (`WorkflowQueueListener.java:65-68`); the catch requeues the first failure and uses `basicNack(..., requeue=false)` after a redelivery (`165-183`). On the Suricata ingestion side, malformed/non-JSON lines and missing required fields are logged/dropped (`SuricataModule.java:371-399`).

### 5.2.8 Literal method sequence (for thesis pseudocode)

19. **Actual Suricata-to-mitigation sequence:**

    1. `SuricataModule.startEveJsonMonitoring()` → `parseEveJsonLine(line, channel)` → `gson.fromJson(..., SuricataEveLog.class)` → `publishSuricataAlert(...)` → `channel.basicPublish("", WORKFLOW_QUEUE, ...)` (`SuricataModule.java:294-334,370-395,405-482`).
    2. `AlertBroadcastListener` consumes ingress/legacy `workflow_queue`; `processMessage()` → `handleAlert()` → `basicPublish` to `alerts_queue` and `workflow_queue` (`AlertBroadcastListener.java:52-95,111-148,200-229`).
    3. `WorkflowQueueListener` consumes `workflow_queue`; it constructs `JSONObject`, calls `workflowLoader.loadWorkflows()`, `workflowMatcher.findMatchingWorkflows()`, then `workflowExecutor.executeWorkflow()` (`WorkflowQueueListener.java:57-68,97-137,187-190`).
    4. `WorkflowExecutor.executeWorkflow()` → `executeStep()` → constructs `workflow_command` → `basicPublish("", workflow_response_queue, ...)` (`WorkflowExecutor.java:30-67,73-165`).
    5. `CommandRoutingListener` consumes `workflow_response_queue`; `routeCommand()` → registry lookup → either `sdkModuleHost.dispatch(json)` or queue publish (`CommandRoutingListener.java:67-84,100-173`).
    6. For embedded ODL, `SdkModuleHost.dispatch()` → `parseMitigationCommand()` → `api.dispatchLocal(event)` → `OpenDaylightModule.onMitigationCommand()` / ODL client action (`SdkModuleHost.java:142-176,210-275`; subscription at `OpenDaylightModule.java:82-86`).

### 5.3 Backend implementation

20. **Threat Context Store is PostgreSQL-backed.** Runtime config targets PostgreSQL at `192.168.159.70:5432/NIS1` (`ThreatContextStore/config.properties:1-6`), and `WazuhAlertDao` inserts event metadata plus `payload` JSON into an `alerts` table (`WazuhAlertDao.java:18-75`). In-memory state includes file-watcher `processedFiles` (`ThreatContextStoreMain.java:82-87`) and listener counters; it is ephemeral. **Caveat:** `schema.sql` creates `wazuh_alerts` (`ThreatContextStore/schema.sql:1-17`), while DAO SQL uses `alerts`; the committed schema and code are inconsistent and deployment must contain the matching `alerts` table.
21. **RabbitMQ is hard-coded at the API level, with no broker abstraction.** Production components import `com.rabbitmq.client` and create `ConnectionFactory`/`Channel` directly (`WorkflowQueueListener.java:3,33-44`; `AlertBroadcastListener.java:10-13,43-68`). `CoreSystemApi` is an API abstraction for embedded modules, but its only concrete host implementation is RabbitMQ-backed (`SdkModuleHost.java:36-94`). There is no Kafka-compatible transport interface.
22. **Registry discovery is file scan plus runtime registration, not hot-loading.** Startup calls `loadModulesFromDatabase()` and then filesystem scanning (`ModuleRegistryMain.java:40-42`; `ModuleRegistry.java:319-326,404-474`). JAR discovery only creates records—it explicitly “does NOT start any processes” (`ModuleRegistry.java:398-402`). Embedded class loading is fixed at startup (`SdkModuleHost.java:289-294`). Therefore a new JAR may appear in registry data after a rescan/restart, but the code does not support dropping a JAR and dynamically loading it into the running core.
23. **Workflow YAML is reloaded per received alert, not parsed once or watched live.** `WorkflowQueueListener` invokes `workflowLoader.loadWorkflows(workflowsDir)` inside its delivery callback (`97-100`), and the loader reads each `.yml/.yaml` file at that point (`WorkflowLoader.java:26-55,62-94`). Changes affect the next message; there is no filesystem watcher or validation/reload transaction.

### 5.5 Topology

24. **The exact as-built host/VM/container topology cannot be confirmed from this repository.** Current configs co-locate RabbitMQ on `localhost` for the three Java services but point PostgreSQL at `192.168.159.70` (`ModuleRegistryLifecycleManager/config.properties:1-19`, `WorkflowEngine/config.properties:1-18`, `ThreatContextStore/config.properties:1-14`). The launcher runs services locally (`start-all.sh:66-93`). Historical/config documentation references other addresses, but no inventory, hypervisor, container definition, VLAN assignment, or topology diagram maps them to Chapter 4 nodes. State this as an evidence gap, not as a confirmed topology match.

## Chapter 6 — Results and Analysis

### 6.Y SDK micro-benchmarks

25. **Recommended precise timer boundaries:** (a) consume-to-deserialize: at the top of `WorkflowQueueListener`’s `DeliverCallback` before line 66, and immediately after `new JSONObject(message)` at line 67; (b) policy match: immediately before/after `workflowMatcher.findMatchingWorkflows(...)` at lines 121-123, optionally separately around `workflowLoader.loadWorkflows()` at 97-100 because it currently dominates “policy” work; (c) command dispatch/publish: immediately before and after `channel.basicPublish` in `WorkflowExecutor.executeStep()` lines 160-165. To include registry dispatch, instrument before/after `routeCommand()` and `sdkModuleHost.dispatch()` at `CommandRoutingListener.java:67-80,160-165`.
26. **Some coarse telemetry/logging already exists, but it is not a valid stage benchmark.** Suricata records generation/receipt timestamps (`SuricataModule.java:411-438`); the executor adds workflow-time telemetry (`WorkflowExecutor.java:141-156`); ODL consumes/logs it through `logTelemetryBenchmark` (called from `OpenDaylightModule.java:580-611`). `WorkflowQueueListener` prints total containment time based on alert timestamp (`141-159`), but its `processingTimeStr` subtracts two consecutive current-time reads (`141-143`) and is not usable. No per-boundary consume/deserialization or matcher duration is logged.
27. **No Micrometer/OpenTelemetry/custom metrics library was found in Maven dependencies or source imports.** Existing instrumentation is hand-built JSON telemetry and `System.out` logging (`SuricataModule.java:427-438`, `WorkflowExecutor.java:141-156`, `ModuleHelper.java:127-143`). Reuse that telemetry envelope or add a small dedicated timer utility; there is no existing metrics hook to configure.

### 6.W Integration / compatibility testing

28. **Mapped Suricata EVE fields:** top-level `event_type`, `timestamp`, `src_ip`, `dest_ip`, `src_port`, `dest_port`, `proto`, `flow_id`, and `action`; nested `alert.signature`, `alert.signature_id`, `alert.severity`, and `alert.category` (`SuricataModule.java:740-785`). Published payload fields are `alert_id`, `signature_id`, `signature`, source/destination IP and ports, protocol, derived severity/category/alert_type/threat_score/confidence_score, plus optional action/flow ID (`SuricataModule.java:443-477`; model declaration `SuricataAlertData.java:18-60`). It does **not** map EVE fields such as rule metadata, flow statistics, HTTP/DNS/TLS/file records, community ID, VLAN, packet/byte counts (the latter two exist in the model but are never set), or arbitrary unrecognised fields.
29. **Concrete failure behavior:** non-`alert` EVE records are silently ignored (`SuricataModule.java:380-383`); alerts without `alert`, `src_ip`, or `dest_ip` are logged then dropped (`385-392`); malformed JSON/other parse exceptions are logged then dropped (`397-399`). Extra JSON fields are tolerated and ignored by Gson’s default deserialization. A bad timestamp falls back to `Instant.now()` rather than failing (`415-424`).
30. **No JUnit tests or `src/test` test classes for `Event<T>`/payload serialization were found.** The repository has manual/tester programs such as `WorkflowEngine/WorkflowTester.java` and `ThreatContextStoreTester/TCSTester.java`, but they are not JUnit assertions. The README claim that each module has tests (`README.md:88-93`) is not supported by test-source files in the tree.

### 6.4 Comparative performance

Reproduce the benchmark under documented conditions, preserve raw logs/CSV, and cite that artifact; do not present ~2 s as a code-confirmed figure.

## Chapter 7 — Conclusion / extensibility evidence

32. **More than one module exists, but only ODL is the concrete response/enforcement module.** Embedded SDK module initialization lists ODL, Suricata HTTP, and Zeek HTTP (`SdkModuleHost.java:289-294`); standalone Suricata and Zeek modules also exist. `PRTGModule` is described as standalone while ODL is SDK-based (`user-defined-modules/README.md:6-25`). This supports multiple integration points, but it does not demonstrate a second production-grade action/enforcement integration equivalent to ODL.
33. **Not in practice for embedded modules.** The registry scans JAR names for registry placeholders (`ModuleRegistry.java:416-456`), but actual embedded loading is the fixed class list at `SdkModuleHost.java:289-294`, called only at registry startup (`ModuleRegistryMain.java:44-49`). A new JAR cannot be dropped into `modules/` and become an active embedded module without at least restart and code/list changes. Do not claim “add without recompiling the core” for the current implementation.
34. **Yes, developer-facing material exists:** `user-defined-modules/README.md` provides SDK/standalone distinctions and build/run instructions (`1-25,43-70`); `SURICATA_MODULE_README.md`, `ZEEK_MODULE_README.md`, `OpenDaylightModule_Plugin.md`, and `SuricataHttpModule_Plugin.md` give module-specific guidance; `WORKFLOW_YML_GUIDE.md` documents playbooks. These are useful appendix inputs, but the generic SDK plugin instructions conflict with the fixed loading code noted in item 33 and should be corrected before reuse.

## General / cross-chapter

35. **Build layout:** root Maven reactor has `nis-thesis-sdk`, `user-defined-modules`, and `ModuleRegistryLifecycleManager` (`pom.xml:21-25`). The SDK is `nis-thesis-sdk` JAR (`nis-thesis-sdk/pom.xml:12-13`); UDMs are one JAR Maven module depending on it (`user-defined-modules/pom.xml:13-30`); registry depends on both (`ModuleRegistryLifecycleManager/pom.xml:24-37`). `WorkflowEngine` and `ThreatContextStore` are standalone javac-based projects launched separately (`start-all.sh:45-53,66-79`; `README.md:71-83`). RabbitMQ, PostgreSQL, OpenDaylight, Suricata, Zeek, PRTG, and the Node dashboard are third-party/external components rather than Maven submodules.
36. **Javadoc readiness is good for the five named SDK public APIs, but generation was not executed because Maven is not installed/on PATH in this environment.** `CoreSystemApi`, `PluggableModule`, `Event`, `ModuleHelper`, and `MitigationAction` have class/method Javadoc (examples: `CoreSystemApi.java:5-61`; `PluggableModule.java:3-61`; `Event.java:7-88`). The POM contains no explicit `maven-javadoc-plugin` configuration (`nis-thesis-sdk/pom.xml:1-47`). Install Maven and run `mvn -pl nis-thesis-sdk javadoc:javadoc`; inspect generated warnings before claiming it is clean.
37. **There is useful commit history and implementation notes, but no single formal Chapter-4 divergence document.** Recent commits include telemetry, mitigation, Suricata, workflow-matcher, and five-test-case changes (`git log`, e.g. `8692c51`, `ade4717`, `3de7444`), and `2026-07-06.md:9-94` records implementation/verification notes. The documents `THESIS_SDK_AND_SYSTEM.md`, `README.md`, and `ModuleRegistryLifecycleManager/SDK_Detailed_Context.md` are design/context material. The reportable divergence is the strongest evidence: SDK Javadoc claims topic-exchange semantics, whereas runtime code uses direct named queues (item 14); and the desired generic plugin model is constrained by a hard-coded embedded class list (item 33).

## Thesis-safe summary

Describe the implementation as a **RabbitMQ queue-based middleware with a mixed module model**: standalone sensor/integration processes and selected SDK modules embedded in the registry JVM. Do not claim topic-exchange routing, universal SDK-based ingestion, hot JAR loading, a container topology, complete YAML semantics, or a measured two-second latency unless those claims are separately implemented and evidenced by an archived test run.
