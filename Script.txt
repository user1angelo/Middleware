# System Component Overview

## RabbitMQ
RabbitMQ acts as the central message bus and "communication fabric" for the system. All major components – the workflow engine, Threat Context Store, user-defined modules, and the module registry – exchange JSON events over RabbitMQ topics. Detection tools and external systems send alerts into RabbitMQ, where they are normalized into a common event format. The workflow engine subscribes to specific event types and triggers workflows when matching alerts arrive. User-defined modules both publish new events (e.g., alerts, enrichment results) and consume workflow commands over RabbitMQ. This decoupled, event-driven model means components can be developed, deployed, and scaled independently while still participating in a unified security workflow.

## Module Registry & Lifecycle Manager
The Module Registry & Lifecycle Manager is responsible for discovering, validating, and controlling the lifecycle of pluggable modules. At startup it scans a configured directory for module JAR files, loads them with a dedicated classloader, and uses reflection to find classes that implement the SDK’s `PluggableModule` interface. Only JARs that correctly implement this interface and initialize successfully are added to the active registry. For valid modules, the manager passes a `CoreSystemApi` handle, which lets them publish and subscribe to events on the communication fabric without knowing low-level details. The registry keeps track of all active modules so the system knows which integrations are available at any given time. On shutdown, it iterates through the registered modules, calls their `shutdown()` methods, and ensures resources like threads, network connections, and file handles are released cleanly. In short, it turns external JARs into first-class, managed components of the platform.

## Workflow Engine
The Workflow Engine executes security playbooks defined as YAML workflows. On startup it parses all workflow `.yml` files and subscribes to RabbitMQ for each trigger event type referenced in those files. When an incoming event matches a trigger, the engine creates a new workflow instance that holds state and context for that particular run. The engine then steps through the workflow definition, executing `action` steps that publish new events (for example, mitigation commands or enrichment requests) and updating the instance’s context as it goes. For `wait_for` steps, the instance pauses while the engine installs a temporary subscription and waits for a matching response event or a timeout. If the required event arrives and meets the conditions, the context is updated and the workflow resumes; if not, the instance is marked as failed and cleaned up. Successful runs terminate once the last step is executed, making the engine a stateful orchestrator that ties together alerts, enrichment, and mitigation actions.

## Threat Context Store
The Threat Context Store is the component that persistently stores security-relevant events and query results in PostgreSQL. Alerts and other standardized messages arriving from RabbitMQ are written into a JSON-capable schema, preserving both core fields (such as timestamps and event types) and rich payload data. This design allows the system to run complex queries over historical alerts, correlate events, and support investigations beyond real-time workflows. The store can also track queries and their status, enabling higher-level components to request data subsets and then consume results from either the database or response queues. By acting as a durable, queryable record of security activity, the Threat Context Store complements the real-time, in-memory behavior of the workflow engine. Together, they enable both immediate automated responses and longer-term analytics.

## User-Defined Modules
User-defined modules are standalone Java components that integrate external tools and systems into the platform. They typically live in the `user-defined-modules` directory and follow a common JSON event model so they can talk to the rest of the system over RabbitMQ. For example, a PRTG module can receive HTTP notifications from a monitoring system and convert them into standardized `alerts.host.prtg` events on the message bus. Similarly, other modules can listen for workflow-driven commands (such as mitigation requests) and translate them into actions against firewalls, SIEMs, or other infrastructure. These modules are developed and deployed independently but are expected to align with the SDK’s message format and event naming conventions. In practice, they are the primary way to plug new tools into the orchestration layer without modifying the core engine.

## OpenDaylight (ODL) Module
The OpenDaylight (ODL) module is a specific user-defined module that connects the platform to an OpenDaylight SDN controller. It listens for workflow-generated commands that describe network mitigation actions, such as isolating a host, blocking a specific IP, or restricting certain protocols. When it receives such a command over RabbitMQ, it translates the high-level intent into OpenDaylight-compatible operations, typically via RESTCONF API calls. This might involve installing or updating flow rules on switches, adjusting VLAN assignments, or mirroring traffic for deeper inspection. Because it follows the same standardized event model as other modules, the workflow engine can treat SDN mitigation as just another step in a YAML-defined playbook. This allows security workflows to move seamlessly from detection to concrete, network-level enforcement.

## SDK
The SDK, implemented in the `nis-thesis-sdk` project, provides the core contracts and helper APIs that make modules pluggable and consistent. At its heart are interfaces like `PluggableModule` and `CoreSystemApi`, which define how modules identify themselves, initialize, shut down, and interact with the event system. The SDK standardizes the JSON message format (including fields like `event_id`, `timestamp`, `event_type`, and `payload`) so that every module speaks the same language. It also offers patterns and examples for publishing events, subscribing to event types, scheduling background tasks, and handling errors robustly. Modules built against the SDK can be discovered by the Module Registry & Lifecycle Manager and immediately participate in workflows without bespoke glue code. Conceptually, the SDK is the developer-facing layer that turns the platform into an extensible SOAR-like framework.

## YAML Workflow Files
YAML workflow files, especially those under `WorkflowEngine/workflows/ransomware`, describe the high-level logic the Workflow Engine should execute in response to specific threats. Each file defines a trigger event (for example, a ransomware-related alert) and a sequence of steps that combine enrichment, correlation, and mitigation actions. Steps can be immediate `action` steps, which publish new events, or `wait_for` steps, which pause execution until a certain response or condition is observed. The workflows reference fields from incoming events, such as source IPs or host identifiers, and then pass those values along to enrichment modules, SDN controllers, or other components. This “policy as code” approach lets you update behavior by editing YAML rather than changing Java code, making it easier to experiment with and refine playbooks. For panelists, these files are where the system’s security strategy and automation logic are explicitly captured.

## PostgreSQL
PostgreSQL serves as the primary relational and JSON-capable database for the system. The Threat Context Store uses it to persist alerts and related data, storing rich JSON payloads in a schema that supports both structured queries and flexible search. Module metadata and health information can also be recorded in PostgreSQL, giving the webapp and other components a reliable source of truth about what modules are registered and how they are behaving. The database underpins reporting, historical investigations, and any functionality that requires durable state beyond the lifetime of a single event or workflow instance. Because the system leans heavily on standardized JSON structures, PostgreSQL’s JSON/JSONB features are a good fit for indexing and querying nested security data. In combination with RabbitMQ, it balances real-time streaming with long-term persistence.

## Webapp (Dashboard)
The webapp is a dashboard that gives users a unified, browser-based view of the entire system. Its frontend, built with React, focuses on a minimalist dark UI that surfaces key pages for system overview, control, logs, workflows, configuration, modules, and testing. From the Control Panel, users can start and stop the core Java programs (Threat Context Store, Module Registry, Workflow Engine) without touching the command line. The Logs and Modules pages stream real-time output and health information over WebSockets so users can immediately see how the system is behaving. Through the Workflows and Configuration pages, users can edit YAML workflows and `config.properties` files directly from the browser, making it easy to iterate on playbooks and settings. Behind the scenes, a Node.js/Express backend exposes REST APIs and WebSocket endpoints, connects to PostgreSQL and RabbitMQ, and proxies system operations for the frontend. Overall, the webapp turns the underlying components into an accessible, operator-friendly experience suitable for demonstrations and evaluation by panelists.
